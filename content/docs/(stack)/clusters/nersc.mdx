title: NERSC
description: Set up the Lightcone Stack on Perlmutter and run analyses on its compute nodes.
---

Run these steps once, on a Perlmutter login node.

<Steps>
<Step>

## Install uv

NERSC doesn't provide uv, but it installs into your home directory:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

uv lands in `~/.local/bin`; make sure that directory is on your `PATH`. git is already installed.

</Step>
<Step>

## Move uv's cache to scratch

Recipes run through uv, which locks files in its cache, and Perlmutter's compute nodes can't lock
files in `$HOME`, where the cache lives by default. Add these lines to your `~/.bashrc`, then open a
new shell:

```bash
export UV_CACHE_DIR=$PSCRATCH/uv-cache
export UV_LINK_MODE=copy
```

The second line tells uv to copy packages from the cache into each project's environment: your
projects live on another file system (see [Where things go](#where-things-go)), where uv can't link
them, and it would otherwise warn every time. A purged cache then costs only a download.

Do this before you launch any compute: an allocation started without it has to be relaunched.

</Step>
<Step>

## Install the Lightcone CLI

With uv's cache on scratch, install the CLI, which provides the `lc` command:

```bash
uv tool install lightcone-cli
```

The install also puts `git-annex` on your `PATH`; if `lc` runs but `git-annex` doesn't, run `uv tool update-shell` and open a
new shell. See [Install the CLI](/lightcone-cli/getting-started#install-the-cli) for more.

</Step>
<Step>

## Install your agent and the plugin

Install [Claude Code](https://docs.nersc.gov/development/coding-agents/claude-code/) or
[Codex](https://docs.nersc.gov/development/coding-agents/codex/) as NERSC's own guides describe, then
add the Lightcone plugin as in the [Quick Start](/quickstart#install-the-lightcone-plugin). The
plugin checks that the CLI is the version it needs when you start a project.

</Step>
<Step>

## Describe Perlmutter's queues

The CLI launches compute from the offers in `~/.lightcone/compute.yaml`. This one has a regular and
an interactive CPU queue, and a GPU queue:

```yaml title="~/.lightcone/compute.yaml"
offers:
  - name: cpu
    provider: slurm
    resources: {cpus: 256, memory: 480}
    max_nodes: 16
    time: {default: 1h, max: 12h}
    startup: batch
    config: {account: myproject, constraint: cpu, qos: regular}
  - name: cpu-interactive
    provider: slurm
    resources: {cpus: 256, memory: 480}
    max_nodes: 2
    time: {default: 1h, max: 4h}
    startup: fast
    config: {submit: salloc, account: myproject, constraint: cpu, qos: interactive}
  - name: gpu
    provider: slurm
    resources: {cpus: 32, memory: 128, accelerators: GPU:4}
    max_nodes: 2
    time: {default: 1h, max: 4h}
    startup: batch
    config: {account: myproject, constraint: gpu, qos: regular}
```

Replace `myproject` with your NERSC project, such as `m1234`. The two CPU offers have the same shape, so
`lc compute launch --cpus 256 --memory 480` takes the regular queue, and `--startup fast` the
interactive one. [Configuring compute](/lightcone-cli/configuring-compute) explains every field.

Then check what the CLI sees:

```bash
lc compute resources
```

<Callout type="warn" title="Not yet tested at NERSC">
  This configuration hasn't been tested by submitting jobs at NERSC yet. If a launch fails, tell us on
  [Discord](https://discord.gg/EbG6JKuyAx).
</Callout>

</Step>
<Step>

## Add Lightcone Lab to jupyter.nersc.gov

This step is optional: [Lightcone Lab](/lightcone-lab) shows your projects in
[jupyter.nersc.gov](https://jupyter.nersc.gov)'s JupyterLab. NERSC turns off JupyterLab's Extension
Manager and its environment can't be changed, but JupyterLab also loads extensions from your home
directory. Install the workbench there:

```bash
uv pip install --python 3.12 --prefix ~/.local --no-deps jupyterlab-lightcone
```

Then restart your server: in JupyterLab, **File › Hub Control Panel**, **stop** your server and
**start** it again. The launcher now has a **Lightcone Lab** section, beside NERSC's kernels.

This is the [workbench only](/lightcone-lab/getting-started): it runs in the browser, and its
**claude** and **codex** buttons start your agent in a terminal in the project folder, with the `lc`
you installed above. `--no-deps` skips the packages of the server features, which NERSC's JupyterLab
can't load. The command also leaves an unused copy of the package in `~/.local/lib/python3.12`.

JupyterLab at NERSC starts at the file system's root, `/`. To create a project, browse to your home
or project folder first, or give **New Lightcone project** a full path such as
`/global/homes/u/user/my-analysis`.

To update Lab, run the install command again with `--upgrade`; to remove it, run
`uv pip uninstall --python 3.12 --prefix ~/.local jupyterlab-lightcone`. Restart your server after
either.

</Step>
</Steps>

## Where things go [#where-things-go]

Perlmutter's [file systems](https://docs.nersc.gov/filesystems/) differ in what they keep: home and
the Community File System (CFS) are permanent, while
[scratch is purged](https://docs.nersc.gov/filesystems/perlmutter-scratch/#file-system-purging) of
files not used for 8 weeks. Keep everything you need to keep off scratch:

| What                                                  | Where                                 | Why                                                                     |
| ----------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------- |
| uv, `lc` and `git-annex`                              | `~/.local`, in home                   | Small, permanent and on every node                                      |
| Lightcone Lab                                         | `~/.local/share/jupyter`, in home     | Where NERSC's JupyterLab looks for your extensions                      |
| uv's cache                                            | `$PSCRATCH/uv-cache`                  | Large and rebuilt on demand; compute nodes can't lock files in home     |
| Your projects, with their environment (`.venv`)        | Home, or CFS for large or shared ones | Permanent; a purge would delete the analysis and its record             |
| Codex's state, inside an allocation                   | `$PSCRATCH/codex`                     | See [the callout below](#where-to-work)                                 |

## Where to work

**From a login node.** Start your agent in your project on a login node, where
[NERSC recommends](https://docs.nersc.gov/development/coding-agents/) running coding agents. Login
nodes limit each user to 30 GB of memory and 12.5% of the CPUs, and refuse local compute, so your
recipes run in Slurm allocations the CLI launches from your offers. Each allocation queues like any
job: the interactive offer usually starts within minutes, the regular one may wait.

**Inside an allocation.** To choose the node yourself and skip the queue between steps, open an
[interactive allocation](https://docs.nersc.gov/jobs/interactive/) and start your agent on the compute
node:

```bash
salloc --nodes 1 --qos interactive --time 01:00:00 --constraint cpu --account m1234
```

The CLI then runs recipes on that node through its built-in local offer, which uses one node, so ask
for one. For GPUs, use `--constraint gpu --gpus 4`; the CLI uses the GPUs listed
in [`CUDA_VISIBLE_DEVICES`](/lightcone-cli/configuring-compute#local-gpus). An interactive allocation
lasts at most 4 hours, and NERSC cancels the request if no node is free within 6 minutes. Your agent
must also be able to reach its service from the compute node.

<Callout type="warn" title="Codex file locking on compute nodes">
  Codex uses file locks under `~/.codex` by default, but Perlmutter's compute nodes
  [do not support file locking on `$HOME`](https://docs.nersc.gov/connect/vscode/#running-on-a-compute-node).
  This can cause errors when running Codex inside an interactive allocation. To keep Codex's state
  off `$HOME`, run this before starting Codex:

  ```bash
  export CODEX_HOME="${PSCRATCH:?PSCRATCH is not set}/codex"
  mkdir -p "$CODEX_HOME"
  chmod 700 "$CODEX_HOME"
  ```

  Reuse this location across jobs to retain session history; add the export to `~/.bashrc` to make
  it persistent. Existing settings and history are not migrated automatically, and you may need to
  sign in again. Back up important sessions: [scratch files may be purged after 8 weeks without access](https://docs.nersc.gov/filesystems/perlmutter-scratch/#file-system-purging).
</Callout>
