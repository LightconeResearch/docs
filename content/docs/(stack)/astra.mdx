ASTRA stands for **Agentic Schema for Transparent Research Analysis**. It is an open specification
for recording a research analysis in `astra.yaml`: what you want to learn, which data and methods
you use, what you produce, and which evidence supports your conclusions.

The aim is to let someone build on a result without having to reconstruct the reasoning behind it.
A reader should be able to follow a claim to its supporting output, inspect the choices that shaped
that output, and find the earlier work that informed those choices. The same record should be
readable by a scientist and by an agent helping with the next analysis.

## What an analysis records

| Element | What you record |
| --- | --- |
| Inputs | Datasets, files and references to other analyses |
| Outputs | The metrics, figures, tables and other artifacts the analysis produces |
| Recipes | Commands that produce outputs from declared inputs and decisions |
| Decisions | Methodological choices, their options and the reasons for considering them |
| Universes | Selections of decision options to evaluate together |
| Prior insights | Existing claims and evidence that inform the analysis |
| Findings | Claims made by this analysis, with supporting evidence |

ASTRA describes the work independently of the software that executes or displays it. In the
Lightcone Stack, the [CLI](/lightcone-cli) runs recipes, [Agent Skills](/agent-skills) help write the
record, and [Lightcone Lab](/lightcone-lab) displays it. The schema and full reference live at
[astra-spec.org](https://astra-spec.org/latest/).

## How claims chain together

Consider a measurement of the baryon acoustic oscillation (BAO) distance scale. Earlier studies
inform a choice of reconstruction method or damping prior. That choice affects a fit, which
produces a distance table. A finding interprets the table. A later analysis may use those distances
to constrain a cosmological model.

The connections have different meanings:

1. A **prior insight** records a claim from earlier work and points to its evidence, such as a
   passage in a paper.
2. A **decision option** can name the insights that support choosing it.
3. An **output** declares the inputs and decisions its recipe uses.
4. A **finding** states what you conclude and points to the output that supports it.
5. In subsequent work, that conclusion can inform a new decision, or its result file can become
   an input to another analysis.

Prior insights and findings share the same claim-and-evidence structure. Their placement tells you
whether the knowledge is being brought into the analysis or reported as a result. Reusing a finding
still requires checking its scope: a method that worked for one dataset may not suit another.

ASTRA supports nested analyses and inputs that refer to separate ASTRA records. Those are building
blocks for connecting research across projects and publications. The broader vision from the
Pittsburgh talk is a paper whose claims open into this record, with links continuing into the work
it uses and the work that uses it.

<Callout title="What is available today">
ASTRA can describe these relationships, and MySTRA can render references to them. The Lightcone CLI
currently executes flat analyses; nested analyses are not yet runnable with `lc`. A browsable network
across publications is a longer-term goal. ASTRA also does not yet record which individual input
produced a particular table cell: the dependency record belongs to the output as a whole.
</Callout>

## Decisions and universes

A decision makes a choice explicit. For example, fitting a relation with ordinary least squares or
a robust method may change how outliers influence the result:

```yaml title="astra.yaml (excerpt)"
outputs:
  - id: fit_params
    type: table
    format: csv
    description: Slope, intercept and scatter for the fitted relation.
    inputs: [catalog_data]
    decisions: [fit_method]
    recipe:
      command: >-
        python src/fit_period_luminosity.py
        --catalog {inputs.catalog_data}
        --method {decisions.fit_method}
        --out {output}

decisions:
  fit_method:
    label: Fitting method
    rationale: Compare the sensitivity of the fit to outliers.
    default: ordinary_least_squares
    options:
      ordinary_least_squares:
        label: Ordinary least squares
      robust_linear:
        label: Robust linear fit
```

A **universe** selects an option for each decision. Its name identifies one configuration of the
analysis; it does not refer to a physical universe.

```yaml title="universes/baseline.yaml"
id: baseline
description: Ordinary least-squares fit.
decisions:
  fit_method: ordinary_least_squares
```

Together, the configurations you explore form a **multiverse**. Comparing them helps you assess
how a conclusion depends on the choices you made. You decide which alternatives are worth testing;
declaring options does not mean the CLI runs every possible combination.

## Evidence and its limits [#evidence]

Evidence can refer to a paper by DOI or to an output of the analysis. For a paper, an exact quote
and a page location help a reader check the passage supporting the claim. Decision options can
then refer to the relevant prior insights by ID.

`astra validate --verify-evidence` checks quoted text against cached source PDFs. A successful match
means the text was found; you still need to judge whether the passage supports the claim and whether
it applies to your analysis. Artifact-backed evidence is currently reported as skipped because
artifact quote verification is not implemented.

## Where MyST and MySTRA fit

[MyST](https://mystmd.org/) is a document engine for scientific writing, with Markdown, equations,
citations, cross-references and publication formats. You write the argument in MyST and choose what
the reader sees. [MySTRA](/mystra) is the plugin that brings ASTRA records and result files into that
document.

For an analysis with a `fit_method` decision, a `fit_params` table and a `fit_plot` figure,
the report can name the selected method, read the slope and embed the plot:

```markdown title="Report excerpt"
With {astra:value}`decisions.fit_method`, the fitted slope is
{astra:value col=slope sig=3}`outputs.fit_params`.

:::{astra} outputs.fit_plot
:::
```

These paths refer to records in the analysis. MySTRA resolves them when MyST renders the page.
After changing the analysis or its results, rebuild the report to update the references. During a
preview, re-save a Markdown page or restart `myst start` to trigger a render; changes to
`astra.yaml` alone are not watched. The prose still needs review when results change.

## The `astra` command

[astra-tools](https://github.com/LightconeResearch/astra-tools) provides validation and inspection
commands. Run these from the project directory with the version used by the current Lightcone CLI:

```bash
uvx astra-tools@0.2.18 validate
uvx astra-tools@0.2.18 info
```

With no filename, `validate` checks the project's specifications and universe files. To check
literature quotes, cache the cited papers with `astra paper add` first, then run:

```bash
uvx astra-tools@0.2.18 validate astra.yaml --verify-evidence
```

Keep the `version:` field written by `lc init`: it identifies the ASTRA schema, separately from the
tool versions. The [ASTRA CLI reference](https://astra-spec.org/latest/cli/) covers paper caching,
validation and universe generation; the [astra plugin](/agent-skills/astra) describes how an agent
uses those commands.
