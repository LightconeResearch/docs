## Project files [#a-project-is-three-files]

A Lightcone project has an ASTRA specification and a uv-managed environment:

- `astra.yaml` describes inputs, outputs, recipes and methodological decisions.
- `pyproject.toml` declares the software dependencies, and `uv.lock` records their resolved versions.
- `.python-version` pins the interpreter. The local `.venv` is built from the lock and can be recreated.

Add dependencies with `uv add`, then commit the changed project files before materializing results:

```bash
uv add numpy
```

The repository carries the analysis and its history. A fresh clone still needs local setup
(`lc init`), access to any annexed data it will use, and a compute allocation. Compute offers and
allocation state are managed separately; see [Running on a cluster](/lightcone-cli/cluster).

## Output states [#an-output-has-an-identity-and-three-facts-about-it]

Each materialized output has a `.<output_id>.manifest.json` recording its definition, input content
hashes and environment identity. Its committed run record identifies the source revision.

| State | Meaning | What `lc materialize` does |
| --- | --- | --- |
| `current` | The recorded definition, inputs and environment match the project. | Reuses the output. |
| `stale` | The manifest is missing or invalid, the definition or inputs changed, or a later commit changed the output outside its run. | Rebuilds it. |
| `behind` | The definition and inputs match, but the environment has changed. | Reports it and leaves it in place. |

These are build states, not assessments of scientific correctness. For example, adding a plotting
package changes the environment for the whole project. Existing outputs become `behind`, even if
that package cannot affect the numerical fit. You decide whether they need to be rerun:

```bash
lc materialize "$CLUSTER" --refresh
```

`--refresh` also rebuilds `behind` outputs. It leaves `current` outputs alone.

A script edit does not by itself make an output stale. If changing `src/fit.py` should trigger a
rebuild, declare that file as an input and include it in the output's dependencies. The commit
records which code ran; the declared dependencies determine when to rerun it.

## Commits and run records [#everything-is-committed-and-the-tree-stays-clean]

git records the source, metadata and history; git-annex stores data and result content. The
project's attributes route files through git-annex when you use ordinary `git add`.

Materialization starts from a clean working tree so the run can identify the committed code.
Each completed output is committed with its manifest and a run record that `datalad rerun` can
replay.

A failed recipe's partial work is restored. A lost cluster connection or an interrupted client is
different: recipes may still be running. Follow the
[interruption guidance](/lightcone-cli/commands/materialize#the-runs-contract) before removing
stray result files.

Use `lc materialize` to write final outputs. A result changed and committed outside its recipe run is classified as stale. Uncommitted edits
still prevent materialization, even when the status report shows the last committed result as current.

## Execution modes [#two-modes-derived-from-the-project]

In **direct mode**, recipes run in the project's locked environment. The CLI uses Landlock on
Linux or Seatbelt on macOS when available to restrict file access and writes.

Adding `[tool.lightcone.image]` to `pyproject.toml` selects **containerized mode**. The CLI builds
an image from that declaration and saves it as versioned content in the repository.

Manifests record the enforcement used for the run. A host without a supported sandbox can run
with reduced isolation; inspect the sandbox report instead of assuming every host provides the
same boundary. See [Sandbox internals](/lightcone-cli/internals/sandbox) for the permitted paths
and enforcement details.

## Inspect or check [#reading-and-gating-are-different-verbs]

`lc status` shows output states and their producing commits. It works with uncommitted edits and
returns success when it can read the project, even if outputs are stale.

`lc materialize --check` is useful in scripts: it exits 1 if materialization would have work to do.
It does not need a compute allocation. Both commands support `--json`; the check report's `ok`
and `up_to_date` fields describe success and whether work remains.

## Prepare a publication [#publication-is-a-license-away]

With a `license` under `[project]` in `pyproject.toml`, materialization maintains
`ro-crate-metadata.json`. This [RO-Crate](https://www.researchobject.org/ro-crate/) describes the
project, its outputs and the runs that produced them.

Generating metadata does not upload or deposit the project. Before sharing an archive, retrieve
the annexed content and use an archive method that includes the actual files. A plain `git archive`
contains the git-tracked annex pointers, not the data bytes. See the
[publication step](/lightcone-cli/getting-started#7-publish) for an archive command.
