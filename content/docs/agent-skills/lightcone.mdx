title: The lightcone plugin
description: How an agent scopes, implements and writes up a Lightcone analysis with you.

The `lightcone` skill guides an agent through work on a Lightcone project. It covers the interview,
implementation, compute, result checks and report updates. The bundled
[`astra` skill](/agent-skills/astra) supplies guidance for the specification itself.

Use it when starting or resuming a project, changing methods, running recipes, diagnosing failures
or preparing a report. You can describe the task or use the
[explicit skill command](/agent-skills#call-a-skill).

## Working with you

The skill tells the agent to record proposed decisions in `astra.yaml` as the discussion develops,
so you can review the actual specification. It keeps context for later sessions in the project's
`AGENTS.md`: constraints, rejected approaches and details the schema does not capture.

Before a long run, a remote allocation or a switch to containers, the agent should confirm the
scope with you. In an interactive session it asks before installing software and leaves git
identity configuration to you. These are agent instructions; the
[hooks](/agent-skills/hooks) report validation and tool availability.

## Before running commands [#before-it-drives-lc]

The plugin requires `lc` version `0.5.0rc5` or newer. If the
[session-start check](/agent-skills/hooks#lightcone-cli-check) has reported that the CLI is ready,
the agent can proceed. Otherwise it checks `lc --version` and follows the
[installation guidance](/agent-skills/installation#the-lightcone-cli).

## Scoping a new analysis

The agent starts with the research plan. During scoping it edits the specification, universe files
and project notes; implementation follows your review.

1. **Define the question.** What are you trying to learn, and what would count as an answer?
2. **Describe the analysis.** Identify the inputs and expected outputs. Each output needs a file
   format. The CLI currently requires a flat analysis, even though ASTRA supports nested ones.
3. **Review relevant literature**, if you want that step. The agent records claims and evidence
   that inform the methodological choices.
4. **Review the decisions.** Choose defaults, record alternatives and remove choices that do not
   belong in the analysis. The agent regenerates the baseline universe, validates the files and
   summarizes the plan for confirmation.

`lc init` creates the initial project files. A new decision may temporarily leave the baseline
universe incomplete; the final validation should resolve that before implementation begins.

## The literature pass

The agent first agrees on a reading list with you. It searches after the analysis structure is
settled, with a limited number of directly relevant papers, and asks you to approve or adjust the
list.

The skill calls for parallel extraction, with one subagent per paper. Each reads a cached PDF,
extracts claims relevant to the analysis, and checks the accompanying quotes. Failed quotes are
corrected and retried up to three times; anything still unverified is omitted and reported.

The main agent records verified passages as evidence for prior insights and links the insights to
decision options. You review the proposed choices and their defaults. The
[astra plugin](/agent-skills/astra#working-with-literature) explains the evidence checks.

## Resuming a project

The agent reads the specification and project notes, runs `lc status`, and summarizes the current
state before asking what to work on. It should not repeat the initial interview when those files
already answer the questions.

## Getting compute

The agent checks for an existing allocation before launching one. On a workstation it can start
the built-in local allocation and tell you it has done so. The default local offer uses available
CPUs and memory and shuts down after 30 minutes without tasks; site configuration can change that.

For remote compute, multiple nodes or GPUs, the agent presents the requested resources for review
first. It releases allocations it started when the task is finished, unless you ask to keep them.
It leaves allocations started elsewhere alone unless you ask it to stop them.

The [cluster guide](/lightcone-cli/cluster) owns the allocation commands, resource limits and
interruption handling. A failed or timed-out launch may still have created an allocation, so the
agent checks its state before retrying.

## Producing outputs

The agent works through each output in turn:

1. Probe the script with `lc run` on the selected allocation.
2. Add its recipe, file format, inputs and decisions to `astra.yaml`.
3. Commit the edited source and specification files.
4. Run `lc materialize` and inspect the result.

A successful probe is useful for debugging. Final outputs come from materialization, which records
their provenance. See the [CLI tutorial](/lightcone-cli/getting-started) for the commands and
[Core concepts](/lightcone-cli/concepts#an-output-has-an-identity-and-three-facts-about-it) for
`current`, `behind` and `stale`.

The agent should declare scripts as inputs when changes to their contents must trigger a rebuild.
A source-code commit is recorded in provenance, but a script edit alone does not make an output
stale. Changes to decisions also need corresponding changes in the universe files.

## When something fails

The agent reads the CLI's diagnostic and addresses its stated cause. Common examples are an
uncommitted file, an undeclared input, a missing dependency or a script writing to the wrong path.
The [troubleshooting guide](/lightcone-cli/troubleshooting) gives the remedies.

If the client disconnects or a run is interrupted, worker tasks can continue. The agent needs to
stop the allocation by its full ID and confirm that recipes have stopped before cleaning result
files. See [materialization failures](/lightcone-cli/commands/materialize#the-runs-contract).

## The report

The agent updates MySTRA references when it adds, renames or removes outputs and decisions.
Measured values use `{astra:value}` so they are read from the result files when the report renders.

You choose the argument and voice. If a new result contradicts the prose, the agent should point
that out for review. It should also check build diagnostics and unresolved references: a successful
MyST build alone does not show that every reference resolved.

The report renders one universe, currently selected by the first universe filename in lexical
order. The agent should check that selection before preparing a report to share. See
[MySTRA configuration](/mystra/reference/configuration#project-root-and-universe) and
[preview instructions](/mystra/getting-started#preview).

## Publishing

When you ask to prepare the analysis for publication, the agent records authorship and the chosen
license, commits those edits and materializes the project to update its RO-Crate metadata.
Validation and `lc materialize --check` should pass before it reports the project ready to share.

The [CLI publication guide](/lightcone-cli/getting-started#7-publish) covers packaging the actual
data and result files. Creating metadata does not deposit the project on a hosting service.
